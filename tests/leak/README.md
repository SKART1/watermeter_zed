# Проверки обработчика протечки

Harness компилирует **настоящий** `src/app_leak.c` отдельной единицей трансляции.
Stubs заменяют только GPIO, joined, доступ к IAS-атрибутам и отправку сообщений.
Статические переменные модуля не открываются тестам и не сбрасываются тестовым
кодом: каждый сценарий запускается отдельным процессом.

Из корня проекта в Linux/WSL с Python 3 и доступным host GCC/Clang либо TCC.
Для проверки старого обработчика сначала извлеките его из исходного commit:

```sh
mkdir -p build/or-fix
git show 12432b26f478e4b972c07ea3990d21005dbe8f52:src/app_leak.c > build/or-fix/app_leak.original.c
python3 tests/leak/run.py --cc cc --source build/or-fix/app_leak.original.c --expect-baseline-bugs
python3 tests/leak/run.py --cc cc
```

`cc` здесь — установленный компилятор для компьютера, не TC32. Если он называется
иначе, передайте его имя через `--cc`. Извлечение через `git show` не изменяет
рабочий исходник. Локальный `build/` не входит в репозиторий.

`--cc` (или переменная `CC`) и `--cflags` разбираются через `shlex.split` в argv,
без запуска shell. Это позволяет передавать локальный wrapper и include-пути.
Output по умолчанию находится в игнорируемом `build/or-fix/test-binaries/`;
альтернативный задаётся через `--build-dir`. Скрипт не устанавливает зависимости, не запускает TC32,
прошивку, MQTT или сеть. Вывод содержит SHA исходника, версию компилятора,
команду компиляции и результаты каждого сценария. В baseline-режиме известные
ошибки обязаны воспроизвестись с кодом 1 и соответствующей проверкой IAS;
падение процесса, ошибка команд/metadata или ошибка сборки не
считаются воспроизведением бага. Категория `false-clear` означает ложное dry,
`coalescing` — два одинаковых пакета при одновременных границах; второй критерий
проверяет намеренное объединение IAS и не является отдельным воспроизведением
ложного сброса. Фактическое окружение TCC 0.9.27 и результаты текущего этапа
фиксирует ведущий в [отчёте OR](../../docs/or-fix.md).

Покрываются все 16 переходов четырёх устойчивых состояний, включая одновременные
A→B/B→A, перекрытие входов и высыхание последнего; импульсы длиной 1/15/30
проходов, hysteresis мокрого состояния и повтор wet-команд при 32→31→32;
все сочетания switchActions 0/1/2 и неизвестного значения. Проверяются
последовательности OnOff обоих EP4/EP5, ровно один IAS при одновременных границах,
сохранение подтверждённого wet при промежуточном debounce и событии другого входа,
сохранение других IAS-битов, zoneId,
CIE/enrollment, profile и параметры сообщений. Все четыре сочетания UART/debug
проверяют сохранение прежних guards команд при высыхании, включая неподтверждённый импульс.

Сетевые сценарии раздельно управляют joined и потерей доставки: пороги wet/dry
при joined=false/true, событие A offline с последующим B online, высыхание вне
сети. Отсутствие автоматической синхронизации после joined и отсутствие retry
проверяются как **известные ограничения текущего этапа**, а не исправления.

Проверки фиксируют атрибут и каждый исходящий IAS-пакет, поэтому промежуточное
ложное dry не скрывается последующим true. Host harness не проверяет SDK radio,
PM/rejoin, энергопотребление, реальные биндинги, физические контакты или HA.
