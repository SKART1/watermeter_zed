# OR двух входов: программная проверка

16 ноября 2026 года. Реализован только пункт 1 [плана улучшений](improvement-plan.md). Собран локальный кандидат **v2.0.06 / 0x20063001**. На устройство он не установлен; физическая приёмка ещё не выполнена.

## Изменение

В `src/app_leak.c` каждый вход хранит своё подтверждённое состояние: мокро на прежнем пороге debounce 32, сухо на пороге 1. Между порогами состояние сохраняется. После обработки обоих входов общий `ALARM1` получает значение **A OR B**. Поэтому высыхание второй пары, короткий импульс и одновременный переход A→B/B→A не снимают существующую тревогу.

Вместо отдельных IAS-пакетов внутри каждой ветки отправляется один общий снимок за проход обработчика. Основанием остаётся прежнее пороговое событие при `joined=true`, даже если общий OR не изменился. Остальные биты IAS, zoneId, CIE-адресация и endpoint 4 сохранены.

Прежние команды On/Off/Toggle с EP4 и EP5, их порядок, настройки и условия UART/debug сохранены, включая повтор мокрой команды при 32→31→32. Конвертер, endpoints, NV-формат, rejoin и режимы сна не менялись. Автоматической отправки при возвращении связи и повторов потерянных сообщений здесь нет.

## Проверки и команда

Разработчик прошивки изменил обработчик и подготовил `tests/leak/`. Отдельный независимый проверяющий просмотрел патч, соответствие используемых SDK-констант и stubs, матрицу сценариев и журналы. Блокирующих замечаний нет. Ведущий интегрировал результат и выполнил TC32-сборку и проверку образов.

Harness компилирует настоящий обработчик отдельной единицей трансляции. Снимок до исправления соответствует upstream Git blob `391c96125e11d3415c35e044c1475974105212aa` с учётом нормализации окончаний строк. До изменения исходника первый прогон воспроизвёл 12 ложных сбросов. Финальная расширенная матрица дала:

| Обработчик | Результат |
|---|---|
| Исходный | 183 PASS, 14 ожидаемых ложных сбросов, 2 ожидаемых отказа нового критерия объединения IAS |
| Исправленный | **199 PASS**, неожиданных результатов 0 |

Два отказа объединения IAS означают прежние дублирующиеся пакеты при одновременных границах; они отделены от ложного «сухо». Ожидаемый отказ принимается только по соответствующей IAS-проверке, а не по любому ненулевому выходу.

Проверены все 16 переходов четырёх состояний, оба направления перекрытия и передачи протечки между входами, короткие импульсы, промежуточный debounce, каждый исходящий IAS, прочие биты/zoneId/CIE, команды 0/1/2 и неизвестная настройка, все четыре сочетания UART/debug. Сетевые сценарии проверяют прежние joined-ограничения, отдельную потерю доставки и событие одного входа offline с последующим событием второго online. Возврат joined без нового события по-прежнему не синхронизирует IAS — это известное ограничение пункта 2.

Host-проверка: Python **3.12.3**, TCC **0.9.27**, флаги `-std=c99 -Wall -Wextra -Werror -O2`. TCC и заголовки Ubuntu распакованы локально в `build/tools/host-tests/`; системные пакеты и конфигурация не изменялись. Версии и SHA пакетов — в `build/or-fix/host-test-tools.json`. [Описание harness](../tests/leak/README.md).

Для повторения в свежем клоне используйте доступный host-компилятор и извлеките
старый обработчик по инструкции в [README тестов](../tests/leak/README.md).

```sh

```

Исходная проверка выполнялась с локальным TCC через wrapper `build/host-cc.py`.
Wrapper, журналы и остальные архивы в `build/` сохранены локально и в GitHub не публикуются.

Журналы: `build/or-fix/old-handler-tests.log` и `fixed-handler-tests.log`. SHA-256 исходного handler: `70af524fcc6dfdee73a107aa7791600f56e39e0684a135cfa616b29bf2f7b723`; исправленного: `95d636a61b3af572a48a937cc494adb4fbfb64d18862821daae1cb69d070394a`.

## Сборка и образ

Ветка `codex/leak-or`, исходный commit `12432b26f478e4b972c07ea3990d21005dbe8f52` плюс правки: переносимость `makefile`, OR в `src/app_leak.c`, версия 06 в `src/include/version_cfg.h`. Точный патч проверенного образа сохранён локально в `build/or-fix/source.patch`, SHA-256 `a8b85c738eae961ccfe46020ebae451bb91f23c09f012afce27e92313cf11ca2`. Это тестовый кандидат, не upstream-релиз.

Сборка из свежего клона: Windows PowerShell → Ubuntu WSL (x86_64, Python 3.12+).
Сначала сохраняются поставляемые образы, затем скрипт распаковывает pinned TC32 и
GNU Make в локальный `build/tools/`. Системные пакеты не устанавливаются.
Если toolchain уже доступен, шаг настройки можно пропустить и передать свой Linux-prefix.
`save-reference.ps1` выполняется один раз до первой сборки; существующий проверенный backup сохраняется.

```powershell
./scripts/save-reference.ps1
$taskLinuxRoot = (& wsl.exe --distribution Ubuntu --exec wslpath -a -u (Get-Location).Path).Trim()
wsl.exe --distribution Ubuntu --cd $taskLinuxRoot --exec python3 scripts/setup-build-tools.py
./scripts/build-wsl.ps1 -ToolchainPrefix ($taskLinuxRoot + '/build/tools/tc32/bin/tc32') -LogPath build/logs/leak-or-v2.0.06.log
```

TC32 GCC **4.5.1.tc32-elf-1.5**, binutils **2.20.tc32-elf-1.5**, GNU Make **4.3**. Последовательные `make -j1 clean` и `make -j1 all` завершились с кодом 0; предупреждений/ошибок компилятора нет. Конфигурация: `END_DEVICE=1`, TLSR8258, `BOARD_8258_DIY`, UART/debug выключены; остальные параметры и toolchain SHA записаны в `build/or-fix/manifest.json`. ELF: text 150468, data 720, bss 13128 байт.

| `watermeter_zed.bin` | 151204 | `a6328bfaddf0fc3b864d612ba3e366983c20707f55b299b627f2fe5fa2c204b2` |

Это хеши исторической сборки до публикации коммитов, с `BUILD_DATE=20250324`.
Makefile получает дату из последнего commit в `src/`: после публикации новая сборка
будет иметь другую дату и может отличаться по SHA. Эти значения не являются
ожидаемыми хешами любой последующей сборки. Бинарные образы в этой ветке не публикуются.

`scripts/inspect-firmware.py` проверил BIN и OTA: длины/CRC корректны, manufacturer `0x6565`, image type `0x0204`, внутренняя и внешняя версии `0x20063001`, OTA payload совпадает с BIN. Результат — `build/or-fix/inspection.json`. Архив содержит ELF, листинг, исходный снимок, патч, тесты и журналы с манифестом SHA. Все 25 файлов манифеста повторно проверены; поставляемые образы в `bin/` восстановлены из проверенных эталонов. `git diff --check` прошёл.

## Осталось на устройстве

Для OR-кандидата нужны OTA и проверка обеих пар на контрольном устройстве: A мокрая, B намокла/высохла; зеркальный сценарий; высыхание последней пары; короткий импульс. Сопоставлять следует свежие IAS-пакеты и состояние Z2M/HA.

Срабатывание датчика может двигать краны; сохранность биндингов этим этапом не проверялась. Host-тесты и сборка не подтверждают радиодоставку, фактическое исполнение команд, сохранение настроек при OTA или энергопотребление. NAS, Z2M, сеть и устройства в этой работе не изменялись. Пункты 2 и 3 плана остаются отдельными задачами.
